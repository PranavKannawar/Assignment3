## 📋 Field 2: Game Description
```text
This project implements the classic two-player adversarial game of Connect-4 (6 rows by 7 columns, 42 positions) as a real-time competition between two autonomous GPU-driven algorithmic competitors.

The game mechanics require players to drop colored tokens into one of the 7 columns, where pieces fall to the lowest unoccupied slot. The objective is to be the first to form a horizontal, vertical, or diagonal line of four consecutive pieces before the board fills into a stalemate. Connect-4 provides an ideal testbed for parallel computing: with a branching factor up to 7 and over 4.5 trillion valid game positions, decision trees demand massive throughput and low latency.

To ensure compliance with diverse environments—from dedicated multi-GPU servers to Coursera's single-GPU container—the game engine dynamically detects hardware via cudaGetDeviceCount(). When >=2 GPUs are present, Competitor 1 runs on Device 0 while Competitor 2 executes on Device 1. Under single-GPU constraints, the engine spawns dual host threads running separate CUDA execution streams, coordinating turn transitions using persistent filesystem lock files (turn.lock) to eliminate race conditions while guaranteeing mutual exclusion.
```

## 📋 Field 3: Code Description
```text
The codebase is architected in clean, standard C++17 and CUDA without third-party external dependencies, organized into modular components:

1. include/connect4_common.h:
Defines the unified Board struct (42-element flat integer array), __host__ __device__ win-checking routines (horizontal, vertical, and bidirectional diagonals), legal move verification, and the LockSync namespace which encapsulates file-based mutex signaling (turn.lock) for inter-process and inter-thread turn arbitration.

2. src/competitor1_mcts.cu (Competitor 1 - Monte Carlo Tree Search):
Executes a high-throughput parallel rollout kernel (mcts_rollout_kernel). For each candidate move, the GPU launches tens of thousands of concurrent threads across multiple CUDA blocks. Each thread utilizes an inline, state-efficient xorshift32 pseudo-random number generator to simulate random playouts until reaching a terminal win, loss, or draw. Results are aggregated atomically (atomicAdd) to score candidate columns based on win probability.

3. src/competitor2_minimax.cu (Competitor 2 - Depth-Limited Minimax):
Employs an alpha-beta pruned minimax kernel that evaluates game-tree branches up to a configurable search depth (default 5-6 plies). It features an evaluation heuristic scoring 4-in-a-row opportunities, 3-in-a-row traps, blocking requirements, and tactical control of the center column.

4. src/main.cpp & src/game_engine.cpp:
The coordinator spawns dual worker threads representing each competitor. Turn management is arbitrated through file locks (LockSync::waitForTurn and LockSync::setTurn). Every move records timestamps, execution latencies in milliseconds, and board states into both CLI output and a serialized JSON telemetry file (output/game_log.json).
```

```text
The project provides comprehensive multi-tiered visualization:
1. Terminal ASCII Board: Real-time rendering of each move in the CLI, showing token positions ('X' for MCTS, 'O' for Minimax), move column, and GPU kernel execution latency in milliseconds.
```
